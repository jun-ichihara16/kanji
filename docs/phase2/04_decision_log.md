## 1. 論点1: North Star Metric の妥当性検証

### 1.1 問い

KANJI のフェーズ・ユーザー構造において、North Star Metric として何を採用すべきか。

### 1.2 結論

**MSH(Monthly Settling Hosts)を Primary、再利用幹事率を Companion とする「Pair 構成」を採用。**

### 1.3 採用理由

- MSH は「価値完了 × ユニーク × 意思」の3条件を同時に満たす唯一の指標
- 参加者数や金額で膨張せず、CtoCサービス初期 North Star の定石(Airbnb の Active Hosts、Splitwise の Settle-up users)と一致
- KANJI のコア仮説「LINEで完結する精算自動化が、幹事の繰り返し利用を生む」を直接検証できる

### 1.4 検討した代替案

**A. MSH(月間精算完了幹事数)** — 採用 ✅
- メリット: 価値完了 × ユニーク × 意思を同時表現、膨張しにくい
- デメリット: 月次集計が遅い、再利用が見えない

**B. 月間 精算完了イベント数** — サブ指標として併用 △
- メリット: 集計が単純
- デメリット: 1幹事が複数回やると膨らむ、リテンションが見えない

**C. 月間 精算完了金額(GMV的)** — 不採用 ❌
- メリット: ビジネス感はある
- デメリット: 高額1回で跳ねる、PMFと相関薄い

**D. 再利用幹事率(30日)単独** — 単独不可、Companion として採用 ✅
- メリット: リテンション直接表現
- デメリット: 母数が小さい初期は不安定、新規流入が見えない

**E. 累積精算完了幹事数(cumulative)** — 不採用 ❌
- メリット: 右肩上がりに見えやすい
- デメリット: 解約・離脱が見えない虚栄指標

### 1.5 重要な認識

MSH 単独だと以下5つの盲点があるため、Companion 指標が **必須**:

1. ヘビーユーザーと新規流入の区別不可
2. 「嫌々最後までやった」が見えない
3. 参加者→幹事化のループが見えない
4. 立替0円・1人イベントのノイズ混入リスク
5. 月次集計の遅さ

→ これらを補うため、再利用幹事率を Companion に置き、補助指標(週次4週移動 MSH、初回精算完了率、参加経験率、K-factor)を併設する。

### 1.6 参考にした他社事例

- **Airbnb 初期**: "Nights Booked" ではなく "Active Hosts" を見ていた → 供給側の活性度を初期 North Star に置く定石と一致
- **Splitwise**: 「グループを作った人」ではなく「実際に精算行動をした人」をコア指標にしていた → 「精算完了」を価値証拠とする思想と一致
- **メルカリ初期**: 出品「者」のユニークでカウント → 幹事ユニークで MSH カウントする設計と一致
- **Uber 初期**: Weekly Active Drivers(月次より週次) → 週次4週移動 MSH の併用根拠
- **Notion 初期**: WAU ではなく Weekly Active Teams → 「コラボ単位の活性」を見る思想

## 2. 論点2: 「精算完了」の定義

### 2.1 問い

MSH を計測するための「精算完了」をどう厳密に定義するか。

### 2.2 結論

**(D) settlements 全件 is_settled=true + 対象イベント条件 + completed_at 管理を採用。**

具体的には:

1. 対象イベント条件(前置フィルタ): 参加者2人以上、立替1件以上、settlement 1件以上
2. 完了条件: 全 `settlements.is_settled = true`
3. 完了日時: `events.completed_at` に記録(不変)、再完了は `re_completed_at` に記録

### 2.3 検討した代替案

**(A) settlements 全件 is_settled=true(単独)** — 単独不可 ✗
- 理由: settlements が0件のイベントで真空真になりノイズ混入。立替0円イベントなどが MSH に入る

**(B) events.status='archived'** — 不採用 ❌
- 理由: archived は useEffect の副作用で更新される派生状態。計測の真実の源泉にできない。手動 archived 機能追加時に意味が変わるリスク

**(C) (A) AND (B)** — 不採用 ❌
- 理由: useEffect が走らないと (B) が満たされない。クライアント側挙動依存で取りこぼしリスク

**(D) (A) + 対象イベント条件 + completed_at** — 採用 ✅
- 理由: ノイズ除外と堅牢性を両立。集計の真実の源泉として機能する

### 2.4 重要な設計判断

#### 「価値完了」概念の3分離

実装上、以下を明確に区別する:

- 価値完了 = `events.completed_at` が記録された状態(MSH 計測用)
- アーカイブ状態 = `events.status='archived'`(UI表示用)
- 祝福UI発火 = 全 settlement が is_settled(UX演出用)

これらを混同しないよう、コード・ドキュメント上で「精算完了」という言葉を曖昧に使わない。

#### completed_at の不変性ルール

一度記録されたら上書きしない(`AND completed_at IS NULL` ガード必須)。理由:

- 再完了で時刻が動くと、リテンション計算が二重カウントで壊れる
- 「初めて価値を体感した月」を不変に保つことで、ユーザー体験との整合性を保つ

#### エッジケースの扱い

| ケース | 処理 |
|---|---|
| 立替が0件のイベント | 対象イベント条件で除外 |
| 参加者1人のイベント | 対象イベント条件で除外 |
| 全員均等で settlement 0件 | 対象イベント条件で除外(初期判断、後で再評価) |
| 後から立替追加で再構成 | completed_at は最初の値を保持、re_completed_at に記録 |
| 完了→未精算戻し→同月内再完了 | MSH 1回のみカウント |
| 完了→未精算戻し→翌月再完了 | 元の月にカウント、当月は MSH 対象外 |
| テストアカウント | is_test_account ブラックリストで集計除外 |

### 2.5 過去データへの対応

既存 archived イベントには completed_at が空。`updated_at` を `completed_at` に転記して概算で再構成。記録開始前は「概算」と注釈を残し、Gate 0 の合格判定には含めない。

### 2.6 タイムゾーン

`completed_at` は TIMESTAMPTZ で UTC 保存。集計時に Asia/Tokyo へ変換し、JST で月跨ぎを判定する。22:00 JST 完了 = 13:00 UTC が翌日にならないよう、`DATE_TRUNC('month', completed_at AT TIME ZONE 'Asia/Tokyo')` を必ず使う。

## 3. 論点3: 招待トラッキングの実装方式

### 3.1 問い

K-factor 計測と「参加者→幹事化」追跡を、KANJI の制約(LINE 経由のコピペ拡散、個人開発のリソース)下でどう実装するか。

### 3.2 結論

**3層構造(URLパラメータ + DB永続化 + クライアント補助)を採用。**

- 第1層: URL パラメータ `?inv=<token>` — 即時性
- 第2層: invitations テーブル — 信頼性
- 第3層: LIFF state / localStorage — フォールバック

### 3.3 採用理由

K-factor 計測は第1〜2層で十分だが、**「参加者→幹事化」追跡には第3層が不可欠**。URL は瞬間情報で、幹事化のタイミングでは失われている。サーバー側 participants 履歴で補強することで、localStorage 消失にも対応できる。

### 3.4 検討した代替案

**(A) URLパラメータのみ** — 単独不可 ✗
- 致命的弱点: LINE のコピペ伝播で param が欠落しうる、幹事化タイミングで情報が消えている

**(B) DBカラムのみ** — 単独不可 ✗
- 致命的弱点: 判定材料が必要(referrer は LINE 内ブラウザで不安定、IP/UA も特定弱い)

**(C) ハイブリッド(2層)** — 部分採用 △
- 「参加者→幹事化」追跡が困難。第3層が必要

**(D) localStorage のみ** — 単独不可 ✗
- 致命的弱点: ブラウザ変わると消える、iOS Safari の自動クリアで失われる

**(D の発展) 3層構造** — 採用 ✅
- 各層の弱点を相互に補完。実装コストは増えるが信頼性が確保できる

### 3.5 重要な設計判断

#### サーバー側補強(クライアント storage 消失対策)

イベント作成時、クライアント値とサーバー側 participants 履歴を突き合わせ:

- クライアントから来た値(localStorage 由来)
- サーバー側の過去 participants レコード

両方を確認し、いずれかが見つかれば紐付ける。クライアント storage が消えていてもサーバー側履歴で補強できる。

#### Phase 2 で記録する最小4種ログ

過剰なファネル計測はしない。以下の4種で K-factor、参加者→幹事化率、初回精算完了率の主要3指標が出せる:

- `event_created`: events INSERT 時(幹事化検知)
- `participant_joined`: GuestJoin 成功時(招待経路集計)
- `event_completed`: completed_at 記録時(MSH 計測)
- `host_first_completion`: 初回 completed_at 幹事(初回精算完了率)

#### やらないこと

- クリック単位の精緻なファネル計測
- A/Bテスト基盤
- ユーザーセグメント別コホート分析
- 招待リンクのカスタマイズ機能

これらは Phase 2 の規模では統計有意差が出せない、または過剰実装。Phase 3 以降で検討。

### 3.6 エッジケース処理

| ケース | 処理 |
|---|---|
| 招待者不明(直接URL) | redemption_layer = NULL、オーガニック流入として別カウント |
| 複数経路で同じ人が来た | 最後の URL param が勝つ(シンプルルール) |
| 改ざん URL | サーバー側で実在チェック → null に倒す |
| 未ログイン参加 | LINEログイン必須なので発生せず |
| 自己ループ(幹事自身が participant) | K-factor 計算時に除外 |
| 同一人物の複数LINEアカウント | Phase 2 では対策不要(規模リスク低) |

## 4. 論点4: Phase 2 合格ラインの数値感

### 4.1 問い

Phase 2 の成功・失敗をどの数値で判定し、Phase 3 への移行をいつ判断するか。

### 4.2 結論

**6ヶ月観測、2段階Gate、数値2つ + 定性3つの AND ゲート構造を採用。**

- Gate 0(Month 1): 計測基盤稼働確認
- Gate 1(Month 2-3): 学習期 - 定性サイン3つ観測
- Gate 2(Month 4-6): 検証期 - 数値2つ + 定性3つ AND

### 4.3 仮数値からの修正点

仮置き案(v1.0)では以下が問題だった:

- 「3ヶ月で MSH 3倍」 → 早すぎる、6ヶ月で評価へ
- 「再利用幹事率 30日 20%」 → 60日窓を併用、25%に
- 「MSH 50/月」絶対値固定 → 3ヶ月移動平均で30以上に
- 数値だけのゲート → 定性条件を必須化

### 4.4 採用理由

#### 個人開発の現実的グロース速度に整合

LINE 経由の口コミ拡散は「友人グループ間で1回試す → 良ければ別の集まりで使う」という低周波サイクル。飲み会の頻度が月1〜2回の人にとって、再利用判定は2〜3ヶ月かけて初めて1回観測されるレベル。3ヶ月では再現性のある数字が出ない。

#### 数値の絶対値より「構造の質」を見るゲート設計

「MSH 50 だが全員開発者の知り合い」のような偽陽性を防ぐ。早すぎる Phase 3 移行を回避するために、定性条件を必須化:

- K-factor 0.1以上(バイラル成長の最低ライン)
- オーガニック流入比率 30%以上(知り合い経由依存からの脱却)
- 参加者→幹事化が3ヶ月連続(ループが回っている証拠)

### 4.5 検討した代替案

**A. 3ヶ月で結論** — 不採用
- メリット: 早期判断
- デメリット: 個人開発のペースに合わない、再現性のある数字が出ない

**B. 6ヶ月の2段階Gate** — 採用 ✅
- メリット: 学習期と検証期を分離できる、構造の質を見られる
- デメリット: 観測期間が長い、開発者のメンタル消耗対策が必要

**C. 9ヶ月以上の慎重判定** — 不採用
- メリット: 確実性が高い
- デメリット: 競合に先を越されるリスク、開発者モチベーション持続困難

### 4.6 重要な認識

#### 早すぎる Phase 3 移行のリスク

ポイント制度(Phase 3)はオーガニック流入が前提。流入が知り合い経由しかない状態でポイント制度を入れると:

- ポイントを使う先(紹介相手)がいない
- 換金や利用先の設計が空回り
- ユーザーが「これは早期参加特典だな」と察して使わない

→ K-factor 0.1未満では絶対に Phase 3 移行しない。

#### 遅すぎる Phase 3 移行のリスク

逆に、Phase 2 が成立しているのに延々と続けると:

- 既存ユーザーの「次の動機付け」が枯渇
- 競合(Splitwise、PayPay 機能拡張)に先を越される
- 開発者のモチベーション低下

→ Gate 2 充足時点で躊躇せず判断する。

#### グレーゾーン処理

「定性サインは揃ったが数値が未達(MSH 平均15程度)」のケースは、「PMF はしているが拡散していない」状態。Phase 3(ポイント制度)の出番として正しい状況なので、Gate 1 の定性条件 + K-factor 0.05以上を満たせば移行検討OK。数値ハードルは「目安」、最終判断は構造の質で行う。

### 4.7 失敗時の対応

| 状況 | 対応 |
|---|---|
| 成長中だが未達(前月比+10%以上) | Phase 2 を3ヶ月延長 |
| Gate 1 の定性サインA未観測 | ピボット検討 |
| 成長率も定性も停滞 | 撤退判断 |

## 5. 論点5: 初回精算完了率を上げる打ち手の特定

### 5.1 問い

MSH を最短で動かすレバーは何か。離脱率の改善でどこに投資すべきか。

### 5.2 結論

**最大ボトルネック「立替が登録されないまま放置される」段階の解消を最優先。Top 5 施策を ROI 順で実装する。**

優先順位:

1. 一括精算完了ボタン(1日)
2. 立替未登録の自動リマインダー(3-5日)
3. 参加者ごとの立替ステータス可視化(2-3日)
4. LINE共有メッセージのテンプレ自動生成(1日)
5. 立替入力UIのdeep link化(3-5日)

### 5.3 ボトルネック分析(フェルミ推定)

| ステップ | 推定到達率 | 備考 |
|---|---|---|
| イベント作成完了 | 100% | 基準 |
| 参加者を1人以上追加 | 80% | -20% |
| URL を LINE に共有 | 56% | -30% |
| 立替が1件以上登録される | 34% | **-40% 最大の谷** |
| 精算画面を開く | 29% | -15% |
| 全件精算完了 | 20% | **-30% 第2の谷** |

### 5.4 「最大の谷」の特定理由

立替登録の段階で離脱が大きい理由:

- 行動主体が変わる(幹事 → 参加者)
- フィードバックループが弱い(誰が登録済みかが見えない)
- 幹事が「催促」を躊躇する(LINE で何度もリマインドは気が引ける)

→ ここを解消できれば、後続のステップに到達する母数が大幅に増える。

### 5.5 採用理由(各施策)

#### Top 1: 一括精算完了ボタン

- 実装コスト最小(既存の settlements 更新ロジックを bulk update に変えるだけ)
- 効果が即座に出る(精算画面まで来た幹事の完了率を直接押し上げる)
- 計測が単純(ボタン押下イベントログで効果測定可能)
- 副作用がほぼない(UX 悪化要素なし)

#### Top 2: 立替未登録の自動リマインダー

- 最大の谷に直接効く
- 幹事の心理的負担(自分で催促する躊躇)を解消
- LINE Messaging API で実装可能(LINE 内完結)

#### Top 3: 参加者ごとの立替ステータス可視化

- 幹事が「誰がまだか」を一目で把握できる
- 個別催促のきっかけになる

#### Top 4: LINE共有メッセージのテンプレ自動生成

- 共有時の摩擦削減、シェアの心理的ハードルを下げる
- 実装コスト最小

#### Top 5: 立替入力UIのdeep link化

- LINE メッセージから直接立替入力画面へ
- タップ数削減で参加者の入力率向上

### 5.6 やらないこと(過剰最適化リスク)

| 施策 | 却下理由 |
|---|---|
| テンプレート機能(前回メンバーをコピー) | 再利用幹事率が低い段階では効果薄。Phase 2 後半検討 |
| QRコード機能 | 対面シェアの利用シーン未検証 |
| 祝福UI の過剰強化 | 既に十分。完了に到達する母数を増やす方が先 |
| プッシュ通知のリッチ化 | シンプルなテキストで十分効果が出る |
| A/Bテスト基盤 | Phase 2 規模では統計有意差を出せない |
| レシート OCR 入力 | 実装コスト過大、Phase 4 以降 |

### 5.7 リスク管理

- リマインダー疲れ: 1イベント最大2回(24h + 48h)、通知 OFF 設定提供
- LINE API 制限: 月1,000通の無料枠を超えない設計
- 誤操作対策: 一括精算ボタンに確認モーダル
- 効果測定の落とし穴: リリース後2週間は様子見、ノイズに惑わされない

### 5.8 参考にした他社事例

- **Splitwise**: 「Settle up all」1ボタンで完了できる UI → Top 1 の根拠
- **Cash App**: Push通知による行動喚起 → Top 2 の根拠
- **PayPay 送金**: 受取通知タップで即時受取画面 → Top 5 の deep link 化の根拠
- **Slack**: 重要アクションは画面トップ、補助は下部に分離 → 精算画面の UI 設計
- **LINE Pay 割り勘**: 友達リスト連動の参加者選択 → 「前回メンバーをコピー」の根拠(ただし Phase 2 後半検討)

## 6. 論点6: 個人情報・解析の倫理ライン

### 6.1 問い

KANJI は LINE 連携・個人開発という前提下で、収集してよいデータと避けるべきデータの境界をどこに引くか。

### 6.2 結論

**「個人情報保護法・LINE 規約を遵守 + データ最小化 + 透明性 + 削除権の保証」の4原則を採用。Week 0 必須タスクとしてプライバシー基盤を整備する。**

- 収集 OK: 機能必須データ、解析用匿名化済みデータ、補助データ
- 収集 NG: 詳細位置情報、デバイス指紋、連絡先帳、Cookie 横断追跡
- 匿名化方針: user_id を SHA256 + SECRET_SALT でハッシュ化、payload は ID 参照のみ
- 同意取得: オンボーディング時に1回(都度同意は不要)
- 保管期間: growth_events 個別レコードは90日、月次集約は2年

### 6.3 重要な認識

#### 「個人開発だから免責される」は誤り

個人情報保護法は事業規模で適用除外にならない。たとえ無償サービスでも、個人情報を扱う以上は対象事業者となる。最低限のポリシー整備は必須。

#### LINE user_id の扱い

LINE プラットフォーム内では一般的だが、外部サービスに渡す瞬間に個人識別符号としての扱いが厳格化する。Google Analytics 等の解析ツールに生の user_id を送ると、規約違反 + 法令上のリスク。

→ 解析用途では必ず analytics_id_hash 経由で送信。

#### PayPay 番号のリスク

PayPay 番号は金融関連の連絡先として扱うべき。漏洩時のインパクトが大きいため:

- Supabase の RLS で本人と該当イベントの幹事のみ参照可能
- 解析ログには絶対に含めない
- 不要になったら削除する仕組みを Phase 2 後半で検討

### 6.4 検討した代替案

**A. プライバシー対応を Phase 2 中盤で実施** — 不採用 ❌
- 理由: 後追いコストが高い(遡及的な再同意取得など)
- 一度収集したデータの匿名化は技術的に困難

**B. プライバシー対応を Phase 3 移行時にまとめて実施** — 不採用 ❌
- 理由: 実装と乖離したポリシーは法的リスクを生む
- ユーザーが Phase 2 期間中に削除依頼を出した場合に対応不能

**C. プライバシー基盤を Week 0 必須タスクとして実施** — 採用 ✅
- 理由: 後追いコストを回避、実装と整合的、削除依頼にも対応可能

### 6.5 同意取得の設計判断

「都度同意」ではなく「オンボーディング時1回」を採用した理由:

- 都度同意(行動ごとに「これを記録していいですか?」)は UX 破壊的
- 個人情報保護法上も「利用目的を通知・公表」していれば同意不要なケースが多い
- ただし利用目的を後から大幅に変更する場合は再同意が必要(Phase 3 移行時に再同意フローを発火)

### 6.6 削除依頼処理: 完全削除ではなく匿名化

完全削除すると、他参加者のイベントデータが壊れる:

- 過去のイベントから幹事の名前が消えると、参加者が「誰のイベントだったか」分からなくなる
- settlement の参照整合性が壊れる
- growth_events の集計値が遡及的に変動する

→ 匿名化方式を採用。個人特定情報のみ削除し、ID 参照は残す。

### 6.7 落とし穴・個人開発で見落としがちな点

| 落とし穴 | 対策 |
|---|---|
| 「個人開発だから免責」誤認 | 個人情報保護法は事業規模で適用除外にならない |
| LINE user_id の生 GA 送信 | 必ず analytics_id_hash 経由 |
| プライバシーポリシーと実装の乖離 | 実装変更時にポリシーも改訂 |
| 削除依頼への対応漏れ | 受付窓口・処理スクリプトを Week 0 で整備 |
| 利用目的の事後拡大 | 大幅変更時は再同意フロー発火 |
| SECRET_SALT の Git コミット | .gitignore 徹底、Vault 使用 |
| テストアカウントの本番混入 | is_test_account フラグでの除外 |

## 7. v1.0 → v1.1 の主要変更点

### 7.1 戦略レベルの重要変更

#### 変更1: North Star を「単独」から「Pair構成」へ

| v1.0 | v1.1 |
|---|---|
| MSH 単独 | MSH(Primary)+ 再利用幹事率(Companion)の Pair |

理由: MSH 単独だと「ヘビーユーザー10人で MSH=10」と「新規10人で MSH=10」が区別できない盲点があるため。

#### 変更2: Phase 2 観測期間の延長

| v1.0 | v1.1 |
|---|---|

| 単一の数値目標 | Gate 0(基盤)→ Gate 1(学習)→ Gate 2(検証) |

理由: 個人開発の現実的グロース速度から、3ヶ月では再現性のある数字が出ない。

#### 変更3: Phase 3 移行条件の構造変更

| v1.0 | v1.1 |
|---|---|
| MSH 50/月 安定 + 再利用率 20% | 数値2つ AND 定性3つ の AND ゲート |

理由: 「MSH 50 だが全員開発者の知り合い」のような偽陽性を防ぐ。

### 7.2 設計レベルの重要変更

#### 変更4: 「精算完了」定義の精緻化

v1.0 では「全件精算完了」程度の記述。v1.1 では `completed_at` 不変ルール + 対象イベント条件 + 価値完了/アーカイブ/UI演出の3概念分離を明確化。

#### 変更5: 招待トラッキングを3層構造で固定

v1.0 では方式案 (A)〜(D) を提示し選択を保留。v1.1 では3層ハイブリッド方式に確定。スキーマも確定。

#### 変更6: プライバシー基盤を Week 0 必須タスク化

v1.0 では論点として保留。v1.1 では Week 0(実装着手前)の必須タスクとして組み込み。

- ポイント制度の具体設計
- グローバル展開(GDPR / CCPA 対応)の検討
- 暗号化保管(PayPay 番号の pgcrypto 適用)
- A/B テスト基盤の導入是非

#### 幹事ポイントの付与条件メモ(2026-05-19 ユーザー要望)

Phase 3 のポイント制度を設計する際の前提として、以下の方針をユーザーから受領:

- **提携店での予約一定額に達するまで、幹事ポイントは付与しない**(または閾値未満は対象外)
- **その条件はユーザーに対してわかりやすく表示する**(残り金額・進捗ゲージ等)

意図(推定):
- ばらまき型ポイント付与による収益悪化を避ける
- 提携店との Win-Win 設計(送客の対価としての成果報酬)
- ポイントが「実需に紐付く」ことで Phase 3 の経済設計を健全化

Phase 3 設計時に検討する具体論点:
1. 「一定額」の閾値設定(店舗ごと / カテゴリごと / 一律)
2. 月間/年間累計でのカウントか、1イベントごとか
3. 提携店データベース(`docs/kanji_service_design_update.md` 系の検討事項)との接続
4. 「達しない場合」の UX(罰則感を出さない表現)
5. KANJI の流通額(GMV)との連動方法

→ Phase 3 移行判定(Gate 2 通過)後に詳細設計に着手。本論点は Phase 2 中の実装には含めない。

## 9. 議論プロセスのメタ的観察

### 9.1 v1.0 から v1.1 への変化が示すこと

#### 戦略の方向性は v1.0 で正しかった

v1.1 は v1.0 を否定していない。「MSH を North Star に」「精算完了を価値証拠に」「Phase 3 でポイント制度」という大枠は維持されている。

#### 精緻化の方向は「数値の絶対化を避ける」

v1.0 は具体数値を置くことで意思決定を明確にしようとしたが、結果として過度に楽観的・偽陽性に弱い構造になっていた。v1.1 は数値を残しつつ、定性条件と Pair 運用で質を担保する構造へ。

#### プライバシー設計の前倒しが最大の盲点解消

v1.0 で論点として保留していたものを、v1.1 で実装の前提条件として明示化。個人開発でこれを後追いすると致命傷になりかねないため、最も重要な構造的変更。

#### 個人開発の現実への収束

v1.0 は「3ヶ月で結論」というスタートアップ的なペース感だったが、v1.1 は「6ヶ月の Gate 構造」という個人開発の現実に合わせた構造へ。期待値を下げるのではなく、判断を間違えないための時間軸を確保する設計。

### 9.2 議論の進行順序が機能した

論点を以下の順序で議論したことが、戦略の整合性を確保した:

1. North Star Metric(これが揺らぐと全部やり直し)
2. 「精算完了」の定義(North Star の計測ロジック前提)
3. 招待トラッキング(K-factor 計測の土台)
4. Phase 2 合格ライン(ゴール設定)
5. 初回精算完了率を上げる打ち手(North Star を最短で動かす施策)
6. 個人情報・解析の倫理ライン(実装の制約条件、最後に詰める)

依存関係に沿って議論したため、後段の論点が前段の結論を覆すことなく進められた。

### 9.3 Genspark + Claude の協働が機能した

各論点について Claude(本AI)の見解を先に出し、Genspark との突き合わせを想定する構造で進めた。実際には Genspark スレッド内で Claude が議論を進める形になったが、以下の役割分担が有効に機能した:

- Claude の強み: 文脈把握、KANJI 固有の制約理解、論理的な代替案比較
- 検索ツールの強み: 他社事例の具体的引き出し、ベンチマーク数値の根拠

### 9.4 戦略ドキュメントの構造化が将来の改訂を容易にする

4ファイル構成(strategy / implementation / privacy / decision_log)に分けたことで:

- 戦略本体だけ参照したい人は 01 を見る
- 実装着手時は 02 を見る
- Week 0 タスク中は 03 を見る
- 過去判断の根拠を確認したい時は 04 を見る

という役割分担が明確になった。Phase 3 移行時にも、各ファイルを独立して改訂できる構造。

## 10. v1.2 再検討: インタビュー結果反映による優先施策の更新

### 10.1 決定

MSH + 再利用幹事率の North Star Pair は維持する。
一方、優先施策は「立替登録の谷」中心から「催促・未回収・自腹化」を解消する**催促レス設計中心**へ更新する。
品質補助指標として「未集金ゼロ精算完了率」「自腹ゼロ達成率」「精算スピード」「リマインド後支払い完了率」の4種を追加する。

### 10.2 理由

2026-05-07 のインタビュー整理(9件)では:

- 入力面倒は9人中4人で強く支持されたが、催促気まずさも9人中4人、かつ平均温度が高く**強度スコア最大**
- 「面倒だし気を遣う。自己負担で良いやとなる」「集金が一番ストレス」など、幹事が損を飲み込むことで表面上の精算を終えるリスクが見えた
- PayPay 磨き込みは9人中 PayPay 不満は2人、抵抗1人で**反証側**
- 傾斜は9人中5人で最多言及。前提課題として強い

### 10.3 旧判断との関係

旧 Top 5 を否定しない。立替登録の谷は引き続き重要(新 #2 として継続)。
ただし Phase 2 のPMF検証では、幹事が再利用したくなる理由を作る必要があり、心理的負担を下げる催促レス設計を先頭に置く。

### 10.4 ターゲット定義の精緻化

旧「20-30代 幹事 / LINE グループ運営層」を、以下の3セグメントに分解:

1. **Excel傾斜計算の社会人幹事**(第一ターゲット)
2. **大型イベント/コミュニティ運営の半プロ幹事**
3. **ドライブ/旅行系の後出し精算幹事**

価値を感じにくいセグメント:
- 少人数で PayPay 統一済みの固定グループ
- LINE 公式アカウント登録に抵抗が強い層
- PayPay に大金を入れること自体に抵抗がある層
- 参加者視点のみの人(未検証)

### 10.5 Phase 2 でやらないことの明文化

- ❌ 飲食店連携(Phase 3 マター)
- ❌ ポイント機能(Phase 3 マター)
- ❌ 本格レシート OCR(コスト過大、要望1名のみ)
- ❌ 自動デポジット決済(規約・返金が重い)
- ❌ LINE 自動 Push リマインド本格運用(参加者視点未検証)
- ❌ 席決め/アレルギー回収(会計 PMF から逸れる)

### 10.6 Gate 1 / Gate 2 への定性条件追加

- **Gate 1**(学習期)に追加:
  - 3人以上が「催促が楽になった」と明示
  - 1人以上が「自腹を避けられた」と明示
  - 手動リマインドまたはテンプレ利用が実イベントで発生
- **Gate 2**(検証期)補助条件:
  - `post_reminder_completion_rate` が継続的に改善
  - `settlement_speed_p50` が短縮
  - `host_absorbed_cost_rate` が計測可能になっている、または定性で自腹回避が確認できる

数値ハードル(MSH 50/月、再利用幹事率 60日 25%) は据え置き(9件のサンプルでは数値ライン変更の根拠不足)。

### 10.7 サンプルサイズへの留意

- インタビューは9件で実施
- 参加者視点のみのサンプルは0件 → T-305 で追加3名ヒアリングが必要
- KANJI 実利用後評価が弱く、warica/PayPay/Excel 等の代替手段利用者の発言が多い
- → 既存仮説の方向性を「修正する」のには十分だが、「絶対値の判断」には更にサンプル必要
