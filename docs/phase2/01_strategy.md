## 1. エグゼクティブサマリー

### 1.1 Phase 2 のミッション

**「PMF が成立しているかを、再現性のある計測で検証する」**

KANJI は LINE 連携の幹事向け割り勘ツール。Phase 1 でコア機能を完成させたが、利用が任意でばらつきが大きく、本質的な価値検証ができていない。Phase 2 では計測基盤の整備 + 主要レバーの改善を通じて、Phase 3(ポイント制度)に進める構造にあるかを判定する。

### 1.2 6本柱の意思決定サマリー

| # | 論点 | 結論 |
|---|------|------|
| 1 | North Star Metric | MSH(月間 精算完了幹事数)+ 再利用幹事率 の Pair 構成 |
| 2 | 「精算完了」定義 | `events.completed_at` で一意管理、対象イベント条件で前置フィルタ |
| 3 | 招待トラッキング | 3層構造(URLパラメータ + DB永続化 + クライアント補助) |
| 4 | 合格ライン | 6ヶ月観測、2段階Gate、数値2つ + 定性3つの AND ゲート |
| 5 | 優先施策 | インタビュー結果を踏まえ、「催促・未回収・自腹化」の心理コストを解消する催促レス設計を最優先(v1.2) |
| 6 | プライバシー | データ最小化 + オンボーディング同意 + 90日ログ集約 |

### 1.3 Phase 2 リソース計画

- 観測期間: 6ヶ月(標準)、最大9ヶ月(延長時)
- 実装期間: 約6週間(計測基盤2週 + 優先施策4週)
- 判定タイミング: Month 1, 3, 4, 6 の各時点でゲート判定
- Phase 3 移行条件: 数値2つ AND 定性3つの全充足

### 1.4 重要な意思決定原則

- 数値の絶対値より「率と傾向 + 定性条件」を優先
- 個人開発の現実的ペースに合わせ、楽観的な前倒し判定をしない
- 「測れないものは改善できない」を徹底し、計測基盤を最優先実装
- プライバシー設計は実装着手前に必ず確定(後追いは高コスト)

## 2. 前提・スコープ

### 2.1 サービスの前提

- 対象ユーザー: 飲み会・イベントの幹事(20〜30代、LINE中心の人間関係)
- コア価値: LINE で完結する割り勘・集金・リマインドの自動化
- ビジネスモデル: Phase 2 では収益化を行わない(PMF検証フェーズ)
- 開発体制: 個人開発、フルタイム1人換算で週20時間想定
- 技術スタック: LINE LIFF / Supabase / Edge Functions

### 2.2 戦略の前提条件

このメモの判断は以下の前提に立つ。前提が崩れたら戦略を再評価:

| 前提 | 崩れた場合の影響 |
|------|----------------|
| 個人開発、リソース限定 | 実装スコープの再優先付け |
| LINE 経由の口コミ拡散がメイン | チャネル戦略の再設計 |
| PMF 探索フェーズである | 既に PMF 達成なら Phase 3 へ前倒し |
| 早期収益化を目的としない | KPI 体系全面見直し |

### 2.3 スコープ外(Phase 2 で扱わないもの)

- ❌ ポイント制度・収益化機能
- ❌ A/Bテスト基盤
- ❌ 多言語対応・海外展開
- ❌ ネイティブアプリ化
- ❌ 高度な分析ツール(Mixpanel / Amplitude 等の有料プラン)

## 3. North Star Metric と KPI 体系

### 3.1 North Star Pair(最重要指標)

**Primary(主要指標):**

> **MSH (Monthly Settling Hosts)** = 当月内に「自分がホストのイベントで全件精算完了させた」幹事のユニーク数

**Companion(伴走指標):**

> **再利用幹事率(30日 / 60日)** = 過去月 MSH 内の幹事のうち、当月も MSH に入った割合

### 3.2 採用理由

MSH は **「価値完了 × ユニーク × 意思」** の3条件を同時に満たす唯一の指標。参加者数や金額で膨張せず、CtoCサービス初期 North Star の定石(Airbnb の Active Hosts、Splitwise の Settle-up users)と一致する。

ただし MSH 単独だと「ヘビーユーザーと新規流入の区別不可」「リテンション構造が見えない」等の盲点があるため、Companion 指標との Pair 運用が必須。

### 3.3 補助指標(4種)

| 指標 | 定義 | 用途 |
|------|------|------|
| 週次4週移動 MSH | 直近4週のユニーク幹事数 | 月次より早い意思決定 |
| 初回精算完了率 | 初回幹事が精算完了に到達する割合 | Section 6 の効果測定 |
| 新規幹事の参加経験率 | 新規幹事のうち過去にKANJI参加歴ありの割合 | 参加者→幹事化追跡 |
| K-factor(月次) | 1幹事が生む新規幹事数 | バイラル成長の検証 |

### 3.3.1 インタビュー反映後の品質補助指標(v1.2 追加)

2026-05-07 のインタビュー整理(9件)では、精算完了そのものよりも「催促しづらさ」「未回収」「幹事の自腹化」が強いペインとして出た。
そのため MSH を価値到達の主指標として維持しつつ、以下を品質補助指標として併用する。

| 指標 | 定義 | 用途 |
|------|------|------|
| 未集金ゼロ精算完了率 | 精算完了イベントのうち、幹事自腹や未回収がない割合 | MSH の質を確認 |
| 自腹ゼロ達成率 | 幹事が未回収分を吸収せず完了できた割合 | 幹事疲弊の解消確認 |
| 精算スピード | 精算開始から全件完了までの時間中央値 | 催促レス施策の効果測定 |
| リマインド後支払い完了率 | リマインド後に支払い完了へ進んだ割合 | 催促施策の直接効果測定 |

実装上の現実性:
- `自腹ゼロ達成率` は明示的な「幹事が負担にする」UI が無いと正確には測れない。Phase 2 では `growth_events` に `host_absorb_confirmed` を**予約イベントとして定義**し、UI 追加は後段。
- 当面は `unpaid_zero_completion_rate` / `settlement_speed_p50` / `post_reminder_completion_rate` の3指標を先に計測する。

### 3.4 KPI 階層構造

```
North Star Pair
├── MSH(Primary)
│   ├── 週次4週移動 MSH(先行指標)
│   ├── 初回精算完了率(流入後の歩留まり)
│   └── 月次完了イベント数(参考値)
└── 再利用幹事率(Companion)
    ├── 30日窓(短期リテンション)
    ├── 60日窓(中期リテンション)
    └── 新規幹事の参加経験率(→幹事化のループ検証)
        └── K-factor(バイラル成長)
            └── オーガニック流入比率(健全性チェック)
```

### 3.5 除外条件

すべての集計クエリで以下を除外:

- テストアカウント(特定 `user_id` ブラックリスト)
- 立替0円イベント
- 参加者1人イベント
- `settlement` 0件イベント

## 4. 「精算完了」の正式定義

### 4.1 公式定義

イベントが MSH カウント対象となる条件:

**1. 対象イベント条件(前置フィルタ)**

- `participants` が2人以上
- `advances` が1件以上(総額 > 0)
- `settlements` が1件以上生成されている

**2. 完了条件**

- 該当イベントの全 `settlements.is_settled = true`

**3. 完了日時の記録**

- 上記1〜2を満たした最初の瞬間を `events.completed_at` に記録
- 一度記録されたら不変(後の再完了は `re_completed_at` に記録)

### 4.2 「価値完了」概念の整理

実装上、以下の3つは **似て非なるもの** として明確に区別:

| 概念 | 定義 | 用途 |
|------|------|------|
| 価値完了 | `events.completed_at` が記録された | MSH 計測 |
| アーカイブ状態 | `events.status='archived'` | UI表示(一覧振り分け) |
| 祝福UI発火 | 全 `settlement` が `is_settled` | UX演出 |

→ 「精算完了」という言葉をコード・ドキュメント上で曖昧に使わない。MSH に関わるのは **価値完了 = `completed_at`** のみ。

### 4.3 重要な設計判断

**`completed_at` の不変性ルール:**

一度記録されたら上書きしない。SQL 例:

```sql
UPDATE events SET completed_at = NOW() WHERE id = $1 AND completed_at IS NULL;
```

`AND completed_at IS NULL` の条件が必須。

**理由**: 再完了で時刻が動くと、リテンション計算が二重カウントで壊れる。「初めて価値を体感した月」を不変に保つ。

### 4.4 過去データの扱い

既存 archived イベントには `completed_at` が空。`updated_at` を `completed_at` に転記して概算で再構成。記録開始前の数字は「概算」と注釈を残す。

### 4.5 タイムゾーン

`completed_at` は `TIMESTAMPTZ` で UTC 保存。集計時に `Asia/Tokyo` へ変換し、JST で月跨ぎを判定。

## 5. Phase 2 合格ライン・移行条件

### 5.1 観測期間

| 期間 | 内容 |
|------|------|
| 標準: 6ヶ月 | Month 1(基盤)+ Month 2-3(学習)+ Month 4-6(検証) |
| 早期前倒し: 最短 Month 4 | 強いサイン観測時のみ |
| 延長: +3ヶ月 | 成長中だが未達の場合 |

### 5.2 判定構造(2段階Gate)

```
Phase 2 開始
    ↓
Gate 0: 計測基盤稼働確認(Month 1)
    ↓
Gate 1: 学習期 - 定性サイン3つ観測(Month 2-3)
    ↓
Gate 2: 検証期 - 数値2つ + 定性3つ AND(Month 4-6)
    ↓
Phase 3 移行
```

### 5.3 Gate 0: 計測基盤稼働(Month 1)

合格条件(数値目標なし):

- ✅ MSH 集計クエリが正しく動作
- ✅ 招待トラッキングが機能(3層すべて稼働)
- ✅ ベースライン MSH 取得済み
- ✅ `growth_events` ログが安定記録

### 5.4 Gate 1: 学習期(Month 2-3)

**通過条件: 定性サイン3つを各1回以上観測**

| サイン | 判定基準 |
|--------|---------|
| コア幹事の出現 | 3回以上 KANJI で精算完了した幹事が1人以上 |
| オーガニック流入の発生 | 開発者の知り合い経由ではない幹事が1人以上 |
| 参加者→幹事化の発生 | `host_was_participant=true` のイベントが1件以上 |

**参考数値(目安、絶対条件ではない):**

- MSH: 月10〜20
- 再利用幹事率(60日): 15%以上
- 初回精算完了率: 50%以上

### 5.5 Gate 2: Phase 3 移行条件(Month 4-6)

**数値条件(必須2つ):**

| 指標 | 合格ライン |
|------|-----------|
| MSH の3ヶ月移動平均 | 30以上 |
| 再利用幹事率(60日) | 25%以上 |

**定性条件(必須3つ):**

| 条件 | 判定方法 |
|------|---------|
| K-factor が0より明確に上 | 月次 K-factor が3ヶ月連続 0.1以上 |
| オーガニック流入比率 | 開発者の知り合い以外が 30%以上 |
| 参加者→幹事化が継続発生 | 月1件以上が 3ヶ月連続 |

→ **Phase 3 移行 = 数値2つ AND 定性3つ をすべて満たす**

### 5.6 早期前倒し条項(Month 4 時点)

以下を **すべて満たす場合** のみ前倒し検討可:

- MSH 月平均50以上、3ヶ月連続伸長
- 再利用幹事率(60日)40%以上
- K-factor 0.3以上

### 5.7 失敗時の対応(Month 6 未達時)

| 状況 | 対応 |
|------|------|
| 成長中だが未達(前月比+10%以上) | Phase 2 を3ヶ月延長 |
| Gate 1 の定性サインA未観測 | ピボット検討 |
| 成長率も定性も停滞 | 撤退判断 |

### 5.8 グレーゾーン処理

「定性サインが揃っているが数値が未達(例: MSH 平均15)」のケース:

- → これは「PMF はしているが拡散していない」状態
- → Phase 3(ポイント制度)の出番として正しい状況
- → Gate 1 の定性条件 + K-factor 0.05以上 を満たせば移行検討OK

数値ハードルは「目安」、最終判断は構造の質で行う。

## 6. 優先施策 Top 5(催促レス設計中心 / v1.2)

### 6.1 最大ボトルネックの特定

幹事フローの離脱推定(フェルミ推定):

| ステップ | 推定到達率 | 備考 |
|---------|-----------|------|
| イベント作成完了 | 100% | 基準 |
| 参加者を1人以上追加 | 80% | -20% |
| URL を LINE に共有 | 56% | -30% |
| 立替が1件以上登録される | 34% | **-40% 従来の最大の谷** |
| 精算画面を開く | 29% | -15% |
| 全件精算完了 | 20% | **-30% 第2の谷** |

→ **従来の最大の谷**: 「立替が登録されないまま放置される」段階
→ **第2の谷**: 「精算画面で全件押下に到達しない」段階

**v1.2 でのインタビュー反映:**
9件のインタビュー整理(2026-05-07)では、入力面倒(9人中4人言及)よりも「催促気まずさ」が**強度スコア最大(9人中4人 × 平均温度高)**として顕在化。
また「面倒だし気を遣う。自己負担で良いやとなる」「集金が一番ストレス」など、**幹事が損を飲み込むことで表面上の精算を終えるリスク**(自腹化)が見えた。

→ **インタビュー反映後の最重要ペイン**: 「催促・未回収・自腹化」の心理コスト
→ 立替登録の谷も引き続き重要だが、Phase 2 の旗印は**催促レス設計**に寄せる。

### 6.2 ROI 順 Top 5 (v1.2 / インタビュー反映)

| 順位 | 施策 | 着目ペイン | 実装コスト | 期待効果 |
|------|------|-----------|-----------|---------|
| 1 | 催促文面テンプレ + 支払い状況可視化 | 催促気まずさ(9/4) | 1-2日 | ◎ 即時 |
| 2 | 立替登録の谷解消(入力導線/一括導線/deep link) | 立替登録の谷(9/4) | 2-5日 | ◎ |
| 3 | 未集金ゼロ・自腹ゼロの幹事向け可視化 | 自腹化 / 未回収(9/3〜4) | 2-3日 | ◎ |
| 4 | 傾斜テンプレ/AI提案の実用化 | 計算負担(9/5・最多) | 2-5日 | ◯ |
| 5 | 後出し費用・ドタキャン対応 | 再精算 / 未回収(9/3) | 3-5日 | ◯ |

旧 Top 5 (v1.1) の位置づけ:
- 旧 #1「一括精算完了ボタン」→ 新 #2 に統合(立替登録の谷解消の一部として)
- 旧 #2「立替未登録の自動リマインダー」→ Phase 2 では実装せず(参加者視点インタビュー未実施のため自動 Push は危険)。新 #1 の手動テンプレで代替
- 旧 #3「参加者ごとの立替ステータス可視化」→ 新 #3 に統合
- 旧 #4「LINE共有メッセージのテンプレ自動生成」→ 新 #1 に統合
- 旧 #5「立替入力UIの deep link 化」→ 新 #2 に統合
- 旧 PayPay 磨き込み(別所言及)→ 優先度を下げる(9人中 PayPay 不満は2人、抵抗1人で反証あり)

各施策の最小実装コードは `02_implementation_plan.md` を参照。

### 6.3 実装ロードマップ(4週間 / v1.2)

- **Week 1**: 計測基盤(`completed_at` / `growth_events` / 招待トラッキング)+ 新 #1(催促テンプレ + コピーログ)
- **Week 2**: 新 #2(立替登録の谷解消 - 一括ボタン・入力フォーム改善)
- **Week 3**: 新 #3(未集金ゼロ・自腹ゼロの幹事向け可視化)
- **Week 4**: 新 #4(傾斜テンプレ拡張)+ 新 #5(後出し費用対応)着手
- **Week 5以降**: 効果測定・振り返り

実行手順の詳細は `06_execution_plan_v1.2.md` を参照。

### 6.4 やらないこと(過剰最適化リスク)

- ❌ テンプレート機能(再利用幹事率が低い段階では効果薄)
- ❌ QRコード機能(利用シーン未検証)
- ❌ 祝福UI の過剰強化(既存で十分)
- ❌ プッシュ通知のリッチ化
- ❌ レシートOCR入力(実装コスト過大)

### 6.5 リスク管理

- **リマインダー疲れ**: 1イベント最大2回(24h + 48h)、通知 OFF 設定提供
- **LINE API 送信回数制限**: 月1,000通の無料枠を超えない設計
- **誤操作対策**: 一括精算ボタンに確認モーダル
- **効果測定の落とし穴**: リリース後2週間は様子見、ノイズに惑わされない

## 7. Phase 2 マスタープラン(時系列)

### 7.1 全体タイムライン(標準6ヶ月)

- **Week 0**(実装着手前): プライバシー基盤
- **Month 1**: 計測基盤の構築期 → Gate 0
- **Month 2-3**: 学習期 + 打ち手投下 → Gate 1
- **Month 4-6**: 検証期 → Gate 2(Phase 3 移行 or 延長 or ピボット)

### 7.2 各期の概要

**Week 0(実装着手前): プライバシー基盤**

この週を完了するまで Phase 2 実装着手しない。詳細は `03_privacy_policy.md` を参照。

- プライバシーポリシー・利用規約の作成と公開
- オンボーディング同意UI実装
- 解析ID生成ロジック実装
- ユーザー削除依頼の受付窓口設置

**Month 1: 計測基盤の構築期**

詳細スケジュールは `02_implementation_plan.md` を参照。

- スキーマ変更 + `completed_at` 記録ロジック
- 招待トラッキング3層実装
- 集計クエリ整備、ベースライン取得
- → Gate 0 通過判定

**Month 2-3: 学習期 + 打ち手投下**

優先施策 Top 5 の実装(Section 6.3 のロードマップ参照)。各月末で定性サイン3つの観測状況を確認。Month 3 終了時に Gate 1 通過判定。

**Month 4-6: 検証期**

- 数値の3ヶ月移動平均が条件を満たすか継続観察
- 必要に応じ追加施策
- Month 4 時点で「早期前倒し条項」を満たすか確認
- Month 6 終了時点で Gate 2 判定

```markdown
## Phase 2 Month X 振り返り

- MSH: __ 人(前月比 __%)
- 再利用幹事率(30日): __% / (60日): __%
```

## 10. 用語集

| 用語 | 定義 |
|------|------|
| MSH | Monthly Settling Hosts。月間 精算完了幹事数 |
| K-factor | 1幹事が生み出す新規幹事の数 |
| 価値完了 | `events.completed_at` が記録された状態 |
| 再利用幹事率 | 過去月 MSH 内のうち当月も MSH に入った割合 |
| オーガニック流入 | 開発者の直接の知り合い以外からの流入 |
| 参加者→幹事化 | 過去にイベント参加者だった人が、自分でイベントを作成 |
| Gate | Phase 2 内の段階判定ポイント |
| North Star Pair | Primary 指標と Companion 指標の組み合わせ運用 |
